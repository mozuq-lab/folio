# フィードの定期取得とバックログ（Feedly風のさかのぼり読み）

## 目的と背景

利用者は、しばらくFolioを開かなかった後でも、その間に流れた記事を For You でさかのぼって読みたい。Feedlyでは長期間見ていないと1,000件を超える記事がたまっており、それを読み進めていた。

現在のFolioは、画面を開いて「更新」したときにだけブラウザーからRSSを取得する。RSSには直近の記事しか載っていない（はてなブックマークの人気・新着エントリーは1回30件ほど）ため、開いていない間に流れた記事は一度も受け取れない。取得件数の上限を上げても解決しない。Feedlyの1,000件は、Feedlyのサーバーが定期的にRSSを取得してためていた結果である。

そこで、Cloudflare側で購読フィードを定期取得し、記事をD1にためて、端末からさかのぼって読めるようにする。

## 利用者の読み方（利用者の説明）

- 久しぶりに開いたら、一覧で新しい記事から順にさかのぼる。
- 気になる記事は「あとで読む」に保存するか、元記事を別タブで開いて読む。
- 一覧のメインは For You。
- 流し見で通り過ぎた記事は未読のまま残し、まとめて既読にできるようにする。
- 長いと3か月ほど開かないことがある。それより前の記事はさかのぼれなくてよい。
- 購読フィード1つで1日数百件以上流れてくるものはない。

## 目標

- Folioを開いていない間も、購読フィードを定期取得して記事をためる。
- 最大90日分の記事をさかのぼれる。For You でも、新しい順の一覧でも、スクロールで途切れずに読める。
- 表示中の一覧の未読をまとめて既読にできる。
- 数万件の記事があっても、一覧の表示とスクロールが重くならない。

## やらないこと

- RSSに載っていない記事（取得を始める前や、90日より前の記事）の取得。
- サーバー側での For You の並べ替え（理由は「判断した点」）。
- 新着の通知。
- 取得間隔を利用者が画面から変える機能。

## 失敗とみなすこと

- 保存した記事、メモ・ハイライトを付けた記事が消える。
- 同期データ（ライブラリ、4MiBまで）が記事の増加で上限を超え、同期が止まる。
- D1やWorkersの無料枠・制限を日常の利用で使い切る。
- 数千〜数万件で For You やスクロールが目に見えて遅くなる。
- 定期取得が、ログインしていない第三者のリクエストで起動・悪用できる。

## 決まっていること（利用者の決定）

| 項目 | 決定 |
| --- | --- |
| さかのぼれる期間 | 90日（約3か月） |
| 一覧のメイン | For You |
| 流し見した記事 | 未読のまま残す |
| まとめて既読 | できるようにする |
| 過去の記事の保持 | 保存・メモのある記事以外は期限で消してよい |
| For You の並び | 案A：90日分の未読全体を関心度順に並べる（日付の区切りは設けない。関心度が高ければ古い記事が新しい記事より上に来てよい） |
| 購読フィード数 | 約30件（利用者は本人1人） |
| Cloudflareのプラン | 無料プラン（Workers Free）で動かす前提（現在は有料プランだが、無料プランへ切り替える予定） |
| 優先取得 | 優先して取得するフィードを利用者が選べる。想定は5件ほど |

## 設計

### 1. データの置き場所を分ける

| データ | 置き場所 | 理由 |
| --- | --- | --- |
| 定期取得した記事（90日分） | D1の新テーブル `folio_articles` | 数万件になりうるため、4MiBの同期データには入れない |
| 既読・未読 | `folio_articles.read_at` | 既読IDを同期データに持つと、まとめて既読を繰り返すうちに4MiBを超える |
| 保存した記事、メモ・ハイライト・AI回答で参照される記事 | 同期データ（現行どおり `reader.articles` に記事本体も保持） | 90日を過ぎても消さないため |
| 購読フィード、好み、反応、AI設定、ノートなど | 同期データ（現行どおり） | 変更なし |
| 取得済み本文（記事詳細で取得したもの） | 現行どおり記事に付ける。`folio_articles` には保存しない | 1件最大12万文字あり、蓄積すると容量を圧迫する |

同期データの `reader.articles` は「保持対象の記事だけ」を持つように意味を変える。`reader.read` は使わなくなる（移行は「6. 既存データの移行」）。

### 2. D1のテーブル（migrationを追加）

`folio_articles`

| 列 | 内容 |
| --- | --- |
| `user_id` | 利用者ID（`cloudflare-access:<sub>`） |
| `article_id` | 記事ID（現行の `${feed.id}-${hash}` と同じ作り方） |
| `feed_id` | 購読フィードID |
| `url` | 記事URL（同じ利用者内での重複除去に使う） |
| `published_at` | 公開日時（RSSの値。無ければ取得日時） |
| `fetched_at` | 初めて取得した日時 |
| `seq` | 利用者ごとの単調増加の番号。端末の差分取得に使う |
| `read_at` | 既読にした日時。未読ならNULL |
| `updated_seq` | 既読・未読が変わったときに更新する番号（差分取得で既読の変化も配る） |
| `payload` | タイトル・概要・画像・タグ・読了目安分・媒体名のJSON（`Article` から `content` と `contentFetchedAt` を除いたもの） |

主キーは `(user_id, article_id)`。`(user_id, url)` は一意にする。差分取得用に `(user_id, updated_seq)`、期限切れ削除用に `(user_id, fetched_at)` の索引を張る。

`folio_feeds`（定期取得用の購読一覧の写し。3章）

`user_id`、`feed_id`、`url`、`name`、`priority`（0/1）。主キーは `(user_id, feed_id)`。

`folio_users`（定期取得の対象を決める）

`user_id`、`email`、`last_seen_at`。認証済みのリクエストで更新する（1時間に1回まで）。定期取得は、`last_seen_at` が90日以内で、`email` が `FOLIO_ALLOWED_EMAILS` に含まれる利用者だけを対象にする。

`folio_feed_state`（フィードごとの取得状況）

`user_id`、`feed_id`、`last_fetched_at`、`etag`、`last_modified`、`last_error`（失敗の種類だけ。配信元の応答本文は保存しない）。

### 3. 定期取得（Cron Trigger、無料プラン前提）

無料プランでは、定期実行を含む1回の実行あたりCPU時間10ミリ秒・外部へのリクエスト50件までという制限がある。RSSの通信待ちはCPU時間に数えないが、XMLの解析は数える。そのため、1回の実行では少数のフィードだけを処理し、何回にも分けて順番に回す。

- **間隔：** 5分ごとに実行する（`*/5 * * * *`、1日288回。無料枠の1日10万リクエストに対して十分小さい）。`scripts/cloudflare-config.mjs` の `workerConfiguration` に `triggers.crons` を追加し、Worker入口に `scheduled` ハンドラーを足す。
- **1回の処理：** 優先フィードから1件、それ以外から1件の計2件を取得する。どちらも「最後に取得した日時が最も古いもの」を選ぶ。2件で10ミリ秒を超えることが計測で分かった場合は、1回1件（優先と通常を交互）に減らす。
- **優先フィード：** 利用者がフィードごとに「優先して取得」を選べる（最大5件）。設定は同期データの購読情報（`Feed` に任意項目 `priority?: boolean` を追加）に入る。優先フィードが0件のときは、毎回通常フィードを2件取得する。
  - 目安：優先5件・通常25件なら、優先はそれぞれ約25分ごと、通常はそれぞれ約2時間ごとに取得する。
- **購読一覧の読み出し：** 同期データ（最大4MiB）を毎回読んで解析するとCPU時間を使い切るため、購読フィード（ID・URL・優先・表示名）を別テーブル `folio_feeds` に写しておく。同期データの保存（`PUT /api/library`）のたびに、購読情報に変化があれば更新する。
- **取得：** 既存の `fetchFeed`（HTTPS限定・リダイレクト再検査・10秒・2MiB）で取得し、新しい記事を `folio_articles` に追加する。既存の記事は更新しない（既読状態を保つ）。
- **条件付きGET：** `ETag` / `Last-Modified` を `folio_feed_state` に保存し、変化が無ければ304で解析を省く（CPU時間の節約にもなる）。今の `fetchFeed` は未対応なので拡張する。
- **失敗の記録：** 取得や解析に失敗したら `folio_feed_state.last_error` に種類（通信失敗・HTTPエラー・形式エラー・時間切れのおそれ）を記録し、次は別のフィードに進む。同じフィードが失敗し続けても、ほかのフィードの取得を止めない。
- **期限切れの削除：** 1日1回（その日の最初の実行で）`fetched_at` が90日より前の行を、1回あたりの件数を区切って削除する。保存・メモの対象は同期データ側に記事本体があるため、`folio_articles` からは消えてよい。
- **安全性：** `scheduled` はリクエストを受けないので、Accessの認証は通らない。外部から起動できる口（HTTPのエンドポイント）は作らない。
- **取り込み上限：** 1フィードあたり現行の `MAX_ARTICLES`（200件）のまま。
- **大きなフィード：** 解析だけで10ミリ秒を超えるフィードは、無料プランでは取り込めないことがある。画面にそのフィードの失敗を表示して利用者に知らせる。

#### 取得状況の表示と「今すぐ更新」

- フィード管理の画面に、フィードごとの「最後に取得した日時」「失敗の有無」と「優先して取得」の切り替えを出す。優先は5件まで選べ、6件目を選ぼうとしたら上限を知らせる。
- 端末の「更新」ボタンは、サーバーで優先フィードを1件ずつ順に取得するリクエストを送る（1リクエスト1フィード。CPU時間の制限を超えないように分ける）。そのあと差分を取得する。
- フィードを追加したときは、そのフィードだけを即時取得する。

### 4. 端末への配信と端末側の保存

- `GET /api/articles?after=<seq>`：`updated_seq` が `after` より大きい行を、古い順に最大1,000件返す。応答には次の `after` と「続きがあるか」を含める。初回は `after=0`。ログインと同一オリジンの確認は既存のAPIと同じ。
- 端末は受け取った記事をIndexedDBに保存し、利用者ごとに分ける（現行のlocalStorageのキャッシュと同じく、アカウントが変わったら前の利用者の記事を表示・送信しない）。90日を過ぎた記事は端末からも消す。
- 画面を開いたとき、「更新」を押したとき、定期的（5分ごと、画面が表示されている間）に差分を取得する。
- 端末からの「更新」は、3章「今すぐ更新」のとおり、サーバーで優先フィードを1件ずつ取得してから差分を取得する（`POST /api/feeds/refresh?feed=<id>` を優先フィードの数だけ順に呼ぶ）。ブラウザーから直接RSSを取りに行く現行の処理はやめる。
- オフラインで既読にした操作は端末に保存し、接続後に送る。

### 5. 一覧・For You・まとめて既読

- For You は、端末のIndexedDBにある未読記事すべてを候補に、現行の評価（`rankPersonalized` ほか）で並べ替える（案A）。スクロールで30件ずつ表示する（現行の自動読み込みを使う）。
- For You で既読にした記事は、その場では一覧から消さず、既読の印を付けて残す。並び直すのは「更新」したときと画面を開き直したときだけ（スクロール位置がずれないように）。差分取得で届いた新着は、並び直すまで一覧に混ぜず「新着◯件」と知らせる。
- 「すべての記事」・フィードごと・カテゴリーごとの一覧は新しい順。保存済みの一覧は同期データの保存記事を表示する（現行どおり）。
- **まとめて既読**：表示中の一覧（For You、すべて、フィード、カテゴリー。検索・未読のみの絞り込みを含む）の未読を既読にするボタンを一覧の上に置く。確認ダイアログを出し、件数を表示する。サーバーには対象の記事IDを分割して送る（`POST /api/articles/read`、1回最大1,000件）。
- 個別の既読・未読の切り替え、元記事を開いたときの自動既読は現行の挙動のまま、置き場所だけ `read_at` に変わる。
- 「AIで選び直す」の対象は、For You の上位の未読から最大30件（現行どおり）。

### 6. 既存データの移行

- 最初の定期取得または「更新」までの間も一覧が空にならないよう、同期データの `reader.articles` にある記事を、初回に `folio_articles` へ取り込む（`POST /api/articles/import`、1回だけ）。
- 同期データの `reader.read` にあるIDは、取り込んだ記事の `read_at` に反映する。反映が終わったら `reader.read` を空にする。
- 取り込みが終わったら、`reader.articles` から保持対象（保存・メモ・ハイライト・AI回答の参照。`lib/retention.ts` の対象から「既読」を除いたもの）以外を外す。
- 古い画面を開いたままの別端末は、再読み込みするまで新しい形式を扱えない。READMEの更新手順に記載する。

### 7. 件数が増えても遅くならないようにする

- `scoreImportance` はすでに転置索引（`importanceIndex`）を使うが、日本語の2文字単位の索引は記事どうしで重なりやすく、件数が増えると遅くなるおそれがある。30,000件で計測し、目安を超える場合は索引の語を絞るなどで対処する。
- 「ニュースのまとまり」（`clusterStories`）は `groups.find` と `every` の組み合わせで件数の2乗に近く重くなる。対象を直近7日分に絞り、件数に比例する処理にする。
- 目安：未読30,000件で、For You の最初の30件が手元のノートPCで1秒以内に表示されること。テストで処理時間の上限を確かめる。

### 8. 容量とコストの目安（無料プラン）

- 記事1件は約1〜2KB。30フィードで1日1,000件取得しても、90日で約9万行・最大180MBで、D1の容量上限（5GB）に収まる。
- D1の書き込みは無料枠1日10万行。記事の追加（1日1,000件程度）と既読操作で収まる。数万件をまとめて既読にすると1回で枠の多くを使うため、まとめて既読はサーバー側で条件（記事IDの一覧を分割して送る）ごとに処理し、1日の書き込みが枠を超えそうなら途中で止めて翌日に続ける旨を表示する。
- D1の読み取りは無料枠1日500万行。端末は差分だけを取得し、全件を読む処理を作らない。
- Workersのリクエストは無料枠1日10万回。定期実行288回と通常の利用で収まる。

### 9. 無料プランへの切り替えで今の機能に起きうること

1回の処理あたりCPU時間10ミリ秒の制限は、通常の画面表示やAPIにもかかる。次は上限を超えて失敗するおそれがある。今回の改修では作り替えないが、切り替え後に動作を確認し、問題があれば別途対処する。

- 記事本文の取得（`/api/article`、最大2MBのHTMLを解析）
- フィードの即時取得（大きなRSS）
- トップページのサーバー側での組み立て
- OPMLの読み込み（最大500フィード）

## テスト

- 定期取得：新規記事の追加、既存記事を上書きしない（既読が保たれる）、URLの重複除去、条件付きGET（304で解析を省く）、配信元の失敗時に他のフィードの処理を続ける、90日を過ぎた行の削除。
- 取得の順番：優先と通常を1件ずつ、それぞれ最後の取得が最も古いものから選ぶ。優先0件・通常0件・全部優先のときの動き。優先の上限5件。
- 購読一覧の写し：同期データの保存で `folio_feeds` が購読の追加・削除・優先の変更に追随すること。
- API：差分取得の順序と続きの有無、既読の変化が差分に含まれる、他の利用者の記事が返らない、未ログイン・別オリジンを拒否、まとめて既読の上限。
- 移行：`reader.articles` と `reader.read` の取り込みと、保持対象だけが同期データに残ること。2回目以降は何もしないこと。
- 評価の高速化：現行の並び順と同じ結果になること（既存テストを維持）と、30,000件での処理時間。
- 端末：アカウント切り替え時に前の利用者の記事を表示しない、オフラインの既読操作が後で送られる。

## 判断した点（利用者の確認待ちではなく、私が決めたもの）

- For You の並べ替えは端末側で行う。サーバーで並べると開くたびにD1の数万行を読み、無料枠（1日500万行）を使い切るため。
- 既読状態は同期データから `folio_articles` へ移す。既読IDの一覧は、まとめて既読を繰り返すと4MiBを超えるため。
- 定期実行は5分ごと、1回に優先1件と通常1件。無料プランのCPU時間10ミリ秒に収めるため。優先は最大5件。
- 記事の保存は利用者ごと（同じフィードを複数人が購読していても共有しない）。本人限定の運用で件数が少なく、利用者ごとの分離が単純なため。
- 取得済み本文は `folio_articles` に保存しない。
- 1フィードあたりの取り込み上限は200件のまま。
- 端末側の保存先はIndexedDB（localStorageは容量が約5MBのため）。
- 「今日のダイジェスト」「ニュースのまとまり」「新しい発見」「ナレッジノートの質問」は、ためた記事（IndexedDB）と既読状態を対象にする。「ニュースのまとまり」は直近7日分に絞る。AIの要約・比較・回答が記事を参照した時点で、その記事本体を同期データの `reader.articles` に写す（90日を過ぎても参照先が消えないように）。
- 記事詳細で取得した本文は、保存した記事・メモを付けた記事のものだけ同期データに持つ。それ以外はその端末のIndexedDBにだけ置く（同期データの4MiBを本文で使い切らないように）。
- 保持対象の記事（保存・メモ・AI参照）は `folio_articles` から消えても同期データに残るので、その既読状態は同期データの `reader.read` に持つ（保持対象の記事IDだけ。件数が少ない）。それ以外の記事の既読は `read_at` に持つ。
- JSONバックアップは同期データ（購読・好み・保存・メモ・保持対象の記事とその既読）を書き出し、90日分の記事は含めない。古い形式のバックアップを読み込んだときは、中の記事と既読を `folio_articles` に取り込む（6章と同じ処理。何度実行しても結果が同じになるようにする）。画面の説明文もこれに合わせて直す。
- 定期取得の対象は、直近90日以内にFolioを開いた利用者で、かつ許可メール（`FOLIO_ALLOWED_EMAILS`）に含まれる人だけ。認証済みのリクエストで最終アクセス日時とメールを記録する（記録は1時間に1回まで）。

## 実装者に任せる点

- IndexedDBの扱い方（ライブラリを使うか、直接書くか）と、メモリーに載せる範囲。
- `seq` / `updated_seq` の採番方法（D1の制約内で単調増加が保証できれば方法は問わない）。
- 「まとめて既読」ボタンの見た目と確認ダイアログの文言。
- 定期取得の1回あたりの処理上限（時間・フィード数）。
